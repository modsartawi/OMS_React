The rulings this prototype encodes, each traced to source or to the requester. Reject any of them and the block above changes.
RulingWhat and why
File picker only No camera capture. Both audiences already have the file on disk — back-office scans it, the call-centre agent receives it before they can attach it. Camera is a v1+ item if agents ask.
No type dropdown WPF makes you pick image/pdf to get a file filter (:1141-1154). The browser reads the MIME and derives AttachmentType. One control disappears — the same dissolution 199/200/203 kept finding.
Downscale + JPEG Images canvas-downscaled to max 2000px edge at q0.85, then base64. WPF re-encodes in the original format (NphiesHelpers.cs:15) so a 6 MB phone photo goes to the exchange whole. Side effect: PNG becomes real JPEG, so ContentType = "image/jpeg" (Extensions.cs:725) stops lying.
PDF untouched, capped Nothing to downscale. Refused over 5 MB with a "re-scan smaller" message, at the picker.
Fixed title select Seven values, no free text. WPF's free-text default "Id" reaches the payer verbatim; a typo is a data-quality defect at a national exchange. The value sent stays the English string ("Id" keeps WPF's wire value).
Duplicates allowed Two prescriptions are two prescriptions. Sequence already makes each supporting-info row distinct (AuthService.cs:332), so nothing downstream collides — unlike 208's duplicate item, which really does.
Preview + remove Thumbnail from the same data URL that will be sent — WPF's separate NphiesImageViewerController window becomes an inline lightbox.
Detail shows them Thumbnails, click to open, read-only. No new endpoint, no server change.
No size cap exists No MaxRequestBodySize, no RequestSizeLimit, no maxAllowedContentLength in NphiesService or SIS.Api; the DB column is Length(4002) = NVARCHAR(MAX). The ~28.6 MB shown is the un-configured default, not a decision anyone took. NPHIES's own limit is unverified.
