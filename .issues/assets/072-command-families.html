Command families for the eight document commands

Ticket 072 of map 068 · revision 2. Which family each command belongs to, what colour carries it, and which commands take no colour at all. Every value is a POS token; nothing new is invented.

Correction that reshaped this proposal

Revision 1 painted Close Order green with a check mark. That was wrong. In this system “close” means cancel — request-close opens a picker of CANCEL_REASONS (“Customer requested cancellation”, “Item out of stock”, …) and the dialog hint reads “Pick a cancellation reason.”

request-closeask for the order to be cancelled, with a reason
cancel-close-requestwithdraw that ask — the order lives on
closecancel the order
force-closecancel it, overriding whatever blocked the normal path

The consequence is structural, not cosmetic: none of our eight commands is a positive outcome. A till has “Customer Received ✓” because the till completes the happy path. This back office only ever touches the unhappy one — orders complete in the field, never from this screen. So there is no green commit button to colour. The end of our bar is terminal, and it is red.

The proposal — two family colours, a quiet tier, a terminal end

POS ships five families because a till does five different jobs. Our eight commands answer only two questions — “change how this gets delivered” and “work the cancellation round-trip” — so two colours carry the bar. The other four commands don’t want a family: two are the ending, and two are low-stakes chatter.

Fulfilment
--fam-fulfilment · #2E7D5B
POS --fam-fulfil, value kept
Reschedule · Change Store
Changes when or where the order is served, without touching whether it lives. Fully reversible — do it again tomorrow and nothing is lost. The only family on this screen whose members keep the order alive.
Cancellation request
--fam-cancel-request · #5D5A93
POS --fam-admin, value kept
Request Close · Cancel Close Request
The round-trip about cancelling — raising the ask and withdrawing it. Neither cancels anything itself, and each undoes the other, so they are a reversible pair. Indigo, not red: asking is not doing.
Quiet
no family colour · ghost
--ink-2 on --border-strong
Add Note · Return Document
Frequent and low-consequence. A note appends to the audit log and changes no state; Return Document posts nothing at all today. Colouring them spends attention on the two commands that need none.
Terminal end
--danger #C23B41 filled
+ danger-outlined override
Close Order · Force Close
Not a family — a tier. The two commands that end the order, pinned to the far edge and larger. Both are destructive, so the colour is red for both; the override is separated by weight (outlined, not filled) rather than by a second, louder red.

Where the 13 statuses go (ticket 073 owns the final split)

Promoted to the pill rail — a plausible six

  • Overall Status — the one-line verdict
  • Delivery Status — where the goods are
  • Payment Status — is money settled
  • Close Status — is a cancellation pending or done
  • Availability Status — can it even be fulfilled
  • Approval Status — is it cleared to proceed

To the Status card in the summary rail

  • Ready Status · Clear Status · Acceptance Status
  • Consignment Status · Control Status
  • Notification Status · Last Action

Severity uses four POS pill styles — ok (--success), go (--accent, in-flight), warn (--attention), mute (--ink-3, absent) — plus a fifth this screen needs that the POS reference never used: bad (--danger), for a cancelled order. Mapping each coded value to a severity is the map’s open “status → severity” question, sharpened once 073 fixes the six.

Calls this prototype takes — say if any is wrong

“Close Order” is the wrong labelYour call
It reads as complete to anyone who hasn’t been told otherwise — it fooled me for a whole revision. “Cancel Order” would say what it does. The catch is that cancel-close-request then contains the word twice over, so the pair may want renaming together (e.g. Cancel Order / Request Cancellation / Withdraw Request). This is copy only — no behaviour, no endpoint changes — but it is your call whether renaming belongs in this effort or a separate one.
Return Document is quiet, not its own familyRecommended
It posts nothing today (actions.ts calls it a placeholder). The obvious third colour would be POS teal --fam-insurance #0B7C8C — but that teal is the prescription / e-Rx accent on this very screen, so it would collide. If Return Document grows real behaviour it graduates to a family then, with the collision in view.
Force Close is a tier, not a family memberRecommended
It sits at the terminal end beside Close Order rather than in the indigo cluster. Both end the order; one is the sanctioned cancel and one bypasses the guard. Putting them together makes the end of the bar mean exactly one thing: this order stops here.
Document-scoped, with one extension ruleRecommended
Deliveries, BBY Inquiry and Sim get the grammar — escape at the start, quiet tier, terminal end — but no family colour, because none of their actions form a family. A new family colour is minted only when a screen has two or more commands sharing a purpose. That stops ticket 070 over-designing the token set.

What lands in the token set (ticket 070)

Two new family tokens, both POS values under our names — --fam-fulfilment: #2E7D5B and --fam-cancel-request: #5D5A93 — plus --danger-800: #8E2A2F for the outlined override’s text. The other three POS family tokens (--fam-sales, --fam-loyalty, --fam-admin) are not ported: a back office sells nothing, runs no loyalty tier, and “admin” names a nav area rather than a command family. --fam-insurance’s value survives only as the prescription accent, under a name 073 gives it. Notably --success earns no button on this screen at all — it appears in the status rail and nowhere else.
