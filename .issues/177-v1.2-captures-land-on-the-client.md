## Answer

**Resolved 2026-07-28.** The verification surface is green again and the two rulings are made.

### 1. The corpus is reconciled — and it is now TWO tiers, named as such

`payloads.ts` reads the capture shape (`response.body.data`, the renamed step keys) and says out
loud which of its exports are the wire's bytes and which are not. The block that is not lives in
`src/features/callcenter/console/__fixtures__/unreachable-v1_0.json` — named so nobody mistakes one
for a capture, and deliberately **not** in `.issues/assets/136-cc-contract/`, because a tenth
hand-authored JSON beside nine captures is the pattern [857] just deleted. Both drives read that same
file, so the tests and the drives cannot drift apart.

Two legs are held there — `nearMissClasses` and `prereqResolution`, both blocked by [859] — because
the capture's own near-misses are **two unready offers with a blank `offerId`**, which is neither the
three rendering classes ticket 171 was built against nor an offer §3.3 can address.

🚩 **What the capture cost, honestly stated.** Values in five tests moved off the fixture and into
the case, because the real projection does not carry what the v1.0 illustration did: the settled
order has `address: null` (the capture environment reached the loyalty attach, not the address book),
every line has `uomOptions: []` and `atpAtScan.known: false`, and the rebind diff carries no
`deliveryFee` and an always-empty `promotionsMoved`. Each of those is recorded at its site with the
857 note that rules it *expected, not drift*.

### 2. The 07 ruling — **hold both**

The client's promise stays *and* the wire's real answer is asserted beside it:

- `readSubmitResult` still has to make `submitted` and `alreadySubmitted` indistinguishable. That is
  a claim about **this repo**, not about the server, and it has to be true on the day [860] lands
  rather than be written then. `SUBMIT_REPLAYED` is derived from the capture's own `documentNo` —
  once-only is keyed on the transaction id, so there is only ever one number to carry.
- `SUBMIT_RETRY_REFUSED` is the capture's real `409 SESSION_CLOSED { reason: "submitted" }`, and
  `theRetryTheServerCannotAnswerYet` asserts what the console does with it: reads it as a dead
  session (not a submit failure), returns the tab to the start, and **carries no order number
  anywhere** — 860's harm as one assertion that goes red the day it is fixed.

The drive holds both too: the replay leg drives §8.3's promise, and a new `outageThenClosed` leg
drives the capture's answer — the order IS minted, the first response is lost, the retry is refused,
and the number is gone.

### 3. The ship-blocked ruling — **detect and say so**

Owner ruling, 2026-07-28. Of the four paths, **two lied to the agent and two did not**:

| Blocked leg | What the console did | Ruling |
|---|---|---|
| [858] below-ATP acceptance (169) | **Silent.** 200, nothing added, no message | **Fixed here** |
| [858] plant-rebind confirm (167) | **Silent.** 200, plant unmoved, no message | **Fixed here** |
| [859] one-click close (172) | Draws the 404 in the server's own words | Ships as is |
| [860] submit retry (174) | Dead-order screen, way onward offered | Ships as is |

`commitWasSwallowed` is the fix. It draws one console-wide banner (`data-cc-swallowed`) in the same
slot as `REBIND_REFUSED`, dismissible, offering **no retry** — the same id would be swallowed
identically, and a fresh one would be a new action against a real basket. It disappears on its own
when 858 lands.

🚩 **Its first version was unsound, and `/standards-review`'s spec axis caught it.** That version
read `isCommitting(action) && replayed === true` and called it exact. It is not: §4's `replayed`
means *not re-applied*, which is equally true of a commit that **already landed** — §6.4's
crash-between-2-and-3 resolution is by construction a replay answer over an applied mutation, and a
`SESSION_BUSY` retry of a commit reaches it. A banner reading *nothing changed* over a basket that
did move is worse than the silence it replaces, because the agent would act on it.

Checking the captures killed the two obvious repairs as well: **`version` advances on both swallowed
commits** (6→11 and 10→15) because `SaveAsync` blind-increments it (§2.1), and fixture 04's swallowed
commit answers **`hasBelowAtp: true` over zero lines** — the sidecar patch landed where the engine
mutation did not. So neither the version nor the header flag can stand in for *did it apply*.

The function therefore takes `applied` as an argument — *did the thing the agent accepted actually
happen, in the projection just returned* — which is verb-specific by nature and is the only honest
question. The add asks the **basket** (the item's total quantity grew; summed, not line-counted,
because the engine may raise an existing line rather than open one); the rebind asks the **plant**,
against the one the token pinned. `confirm-action.test.ts` is weighted accordingly: one case proves
it fires on the captures, one proves each shortcut is wrong, and four prove it stays quiet —
including the replay-of-an-applied-commit that started this.

### Two real client defects the capture found on the way

Both are the same shape — **a blank `offerId` is a real wire answer**, and this side keyed on it:

1. **The guidance strip drew one card for two offers.** `key={card.offerId}` over two blank ids made
   React de-duplicate them, and opening one opened both. Fixed with `GuidanceCard.cardId` — the
   `offerId` where the wire supplied one, the position in the server's own list where it did not
   (safe precisely because the view model never re-sorts). It is a render key and never an offer
   identity: `offerId` stays blank on the wire and in the data attribute, so 859 stays visible.
2. **`BasketPanel` and `StoreMoveConfirm` keyed promotion rows the same way** — fixed to position.

### Also folded in

The client half of v1.2's two additive request fields: `addItem.uom?` (no caller yet — the picker's
catalogue is empty in phase 1, which 857 confirms as expected) and `setSlot`'s
`day / description / from / to`, which ride from `SlotPicker` because the slot catalogue is not on
this door ([137]) and the CLCN header stamps all five.

⚠ **One assumption to check against [804].** The four slot fields are mapped by literal name from the
`TimeSlotModel` / `TimeSlotTimeModel` the picker already holds — `day: day.day`, `description:
entry.time`, `from: entry.slotFrom`, `to: entry.slotTo`. `CreateDocument :18730-18734` is the
authority on what the header actually wants; if it wants the date rather than the weekday, this is a
one-line change at `SlotPicker.tsx`'s `onPick`.

### Also fixed at review

`/standards-review`'s standards axis found three, all applied: the swallowed banner and 167's refusal
