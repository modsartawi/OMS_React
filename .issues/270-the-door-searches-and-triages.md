# 270 — The door searches, and triages what needs a human

## What to build

The front page. **Nobody browses 1394 branches** — an accountant arrives with a *branch* in mind or
with *work* in mind — so the door is a search box and a triaged worklist, and 269's account is where
both land.

### The search

One box resolving **branch code, branch name in either script, city, or entry number**. An entry
number jumps straight to that entry's branch account; everything else ranks branches. The scope
(below) **ranks** results, it never refuses one.

### The scope control

Three states — **my branches** (default), **unassigned**, **all** — over the assignment the four
collection inquiries already read.

- "Mine" is the **union of own branches + one-level reports**, so a supervising accountant does not
  open empty.
- An accountant with **no staff row opens unfiltered**. That is a normal state, not an error, and the
  screen must not announce it as one.
- **Widening is never locked.** The scope is a convenience, never a permission.

### The worklist, triaged by what it costs

| lane | contents | scope |
|---|---|---|
| **Wrong money** | orphan consumptions (no document, past the server's grace), **enumerated in full**, each with a **Repair** action | 🔑 **always estate-wide** |
| **Cash waiting** | prepared-but-uncollected settlement receipts, showing **age** | 🔑 **always estate-wide** |
| **Ageing** | entries open a long time — **a count and a way through to the ledger**, never a card each | honours the scope |

🔑 **The estate-wide carve-out is the load-bearing part of this ticket.** 1255 of 1394 branches are
unassigned; under a naive "mine" scope their money would be on nobody's screen. Wrong money and cash
waiting are rare, enumerated, and belong to whoever is looking — only the ageing count and the search
ranking honour the scope. Anyone "tidying" the scope handling will break this first, so it gets its
own test.

🔑 **Triage is why this screen works.** The prototype proved the alternative by failing: an untriaged
"needs you" list went from 3 cards at six branches to ~140 at scale, of which 131 were merely ageing,
and the four that were actually *wrong* sank into them.

### The repair action

The wrong-money lane's rows carry **Repair** — the only write on this screen. It calls the server's
repair door, which is **predicated on the consumption still having no document**, so a late Z
arriving mid-click comes back as a **no-op, not a failure**: say so plainly and refresh the lane.

**Also in this ticket**: the **flat cross-estate ledger** as a support view — capped, paged,
filter-first — answering *"find entry #143, whichever branch it is on"*. It is explicitly **not** the
account: it can only assert a total nobody owes and nobody consumes, so render the total as a report
figure and keep the position on 269's account.

## Spine reach

An accountant opens the screen and is taken to the branch, or to the work, without scrolling an
estate.

### What the build settled

**The estate fixture is the deliverable's other half** (`fleet-fixture.ts`): **1394 branches, 1255
unassigned, 24 mine**, 140 ageing entries of which **47** are in scope, and **4** orphan
consumptions. 269's six hostile branches keep their identity inside it — their aggregate rows are
*computed from their own accounts* (`accountHeadline`), never retyped, so the fleet and the account
cannot disagree about a branch — and 🔑 **0331, the orphan branch, is deliberately `unassigned`**, so
the carve-out is visible on screen and not only in a test. Not one Arabic string is retyped: the six
names arrive by import, the 1388 generated branches are English-named by construction. Generated by
a **seeded LCG**, because a drive asserting *"47 entries"* against `Math.random()` asserts nothing.

**Three doors this ticket invented, all logged in `.afk/HITL-270.md` for 274.** D8 could not carry
the screen: its aggregated `FleetRow` says a branch *has* an orphan, and `Settlement/Repair` is keyed
by a `settlementConsumptionId` — so `Settlement/Worklist` enumerates the two lanes and
`Settlement/Ledger` answers *"entry 143, whichever branch it is on"* for both the flat view and the
search box. `FleetRow` gained four fields (`city`, `assignment`, `ageingCount`, `currencyKey`), each
argued at the type.

🔑 **The carve-out is enforced three times over, by shape rather than by comment.** The worklist door
**takes no scope parameter**, so it cannot be narrowed by accident; `buildWorklist` hands the
`ScopeResolution` to exactly one line, and the two enumerated lanes are returned untouched; and the
`AgeingLane` type **carries a count and no row array**, so a card-per-entry is not something a
component could do wrong. The fleet is fetched **once at `scope=all`** and scoped on the client —
otherwise a scoped fetch would need a second estate-wide one beside it, or would quietly drop the
1255 unassigned branches from the lanes.

**Two ambiguities the fixture found that the ticket did not name:**

- 🚩 **`1001` is both a real branch code and a real entry number** — 493 of the fixture's codes are
  live entry numbers. `resolveSubmit` rules that an **exact code wins**; a leading zero is always a
  code (`0142` ≠ entry 142). The failure it prevents is the worst this box can produce: an accountant
  types their own branch's code and lands on a *different* branch's account, plausibly and silently.
- 🚩 **A link that names a branch was throwing the scope away.** `addresses.ts` now owns the screen's
  whole URL grammar as a **keep-list**: every link keeps `?scope=` and drops the view it left. A
  parameter a later slice adds belongs to a view by default, which a drop-list would have got wrong.

**The open question, settled: the worklist refreshes MANUALLY** — a Refresh button beside the lanes,
plus a 60-second `staleTime` so walking into a branch and back is not a re-fetch. The lanes change
when a till closes a shift (hours apart, not seconds), and a triage list that moved rows under a
reader's cursor mid-decision is worse than a stale count.

⚠️ **An entry-number search lands on the entry, not just the branch** (`?store=…&entry=…`) — story
3's own words, and 269's grid selects its first *displayed* row, which after a sort is not the entry
the accountant was quoted.

⚠️ **The ageing lane's *way through* is honest about what it opens.** The count is scoped and past
the server's threshold; the ledger can only filter on what the criteria carry, so the link says
*Browse open entries* and the count says *counted for the branches you have scoped*. Inventing an
`ageing=true` predicate would have been this screen inventing the threshold rule the ticket forbids.

**Six `/code-review` findings, all fixed in-slice** — four of them real defects: the entry-number

**`/standards-review`: no hard violation on either axis.** Three duplications it named were all

## Boundaries

- **The account view is 269's** — this ticket navigates to it and does not restyle it.
- **No posting** (271) and **no correction** (272). Repair is here because it lives on this lane and
  nowhere else.
- **No ageing threshold logic invented here.** The lane shows what the server returns; escalation
  rules are deliberately unsettled.
- **No caching of the fleet aggregate.** The server's open-set aggregate is fast; a denormalised
  per-store balance is the trap this design refused twice.

## Done when

The door opens on my branches, finds a branch four ways, triages the work into three lanes with the
estate-wide carve-out proven by test, and repairs an orphan — including the no-op case.
