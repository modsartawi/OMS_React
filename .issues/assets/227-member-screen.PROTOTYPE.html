The shape of the member screen

Three ways the same screen can go from one field on an empty page to a dense member view. Same data in all three (225's resolve rule, 226's three column sets, 229's code rule, 230's two chips) — what differs is where the search goes once it has done its job, and how much of the member the header carries. Mock data; no server. Not a port of WPF IC.

Variant
Theme
VARIANT A

The field stays put; the member unfurls beneath it

The search card is permanent furniture at the top of the page and never moves. A found member renders below it; a second lookup is just typing again in the same box, which replaces what is below. The box always shows what was typed last. Costs ~86 px of vertical space above a screen whose whole job is scanning long grids, and the member's name is never the first thing on the page. Buys one mental model, zero transitions to design, and the answer to "what did I search?" is always on screen. Simplest thing that could work — which is this map's standing preference.

VARIANT B

The field collapses into an identity bar

TAKEN

Chosen 2026-08-06, with two amendments applied below: the bar carries the searched key only — the name lives in exactly one place, the header — and the resolved member lives at /loy/members/:loyId with the open tab as a query param, so Change reopens the field in place and New lookup navigates to /loy/members.

The call-centre chip-bar move. Before a lookup the field is the page — a hero, centred, nothing else competing. Once a member resolves the field collapses into a slim bar carrying the key that resolved them and a Change affordance; the member view owns the rest of the screen. Clicking Change expands the bar back into the field, pre-filled. Costs a state to design and explain, and the typed value is one click away rather than on screen. Buys ~40 px back for the grids, an empty state that reads as an invitation rather than a form, and it matches a shape the portal already uses — the console's settled-and-collapsed chip.

VARIANT C

A lookup rail beside the member

The search never leaves and never collapses — it lives in a narrow rail down the start edge, with the members looked up this session listed under it. The member view takes the whole remaining width. A second lookup is one field away without displacing anything, and going back to the previous member is one click. Costs ~250 px of width on a screen whose Sales tab already wants eight columns, a session-recents list nobody asked for, and it stacks the rail above the member below ~900 px. Buys the only variant where comparing two members is cheap — which is what a call actually looks like. Furthest from phase 1's "read-only, and simple" preference.

What the three variants agree on — and what is still open

Held constant across all three, so a choice between them does not re-open a settled decision:

  • The header is not a tab. Identity + tier + the points block sit above the tab strip in every variant; the long tail of member fields (email, birth date, gender/nationality/city codes, national ID, language, insurance) lives behind one disclosure, shut by default.
  • Points balance is the headline number — the only 27 px figure on the screen, with the SAR equivalent as its own subline, and pending / expiring / tier points beside it at label size.
  • Activities is the landing tab; Sales and Actions are peers, not secondary. Only the Actions tab carries a count, because it is the only read with a real total (226).
  • Codes are labelled as codes — "City code", "Gender code" (229) — and the raw value is shown in mono so it reads as a key, not a word.
  • Chips are additive and rare: tier always, member-type when not M, blocked when there is a reason. An ordinary Gold member shows one chip.
  • The header scrolls away. None of the three pins it; a long grid gets the whole viewport and the grid's own header is what sticks.

Settled on the back of choosing B:

  • The member is in the URL — /loy/members/:loyId, open tab as a query param (?tab=sales). A lookup navigates, a refresh re-reads by LoyId, a link works for a colleague, and /loy/members bare is the empty field. This closes the map's URL shape and deep-linking fog item. Note the consequence: the URL holds the LoyId, not what was typed, so a refresh after a mobile lookup re-reads by key and does not replay 225's two-call cascade.
  • The bar carries the key, not the member — the name is in the header and nowhere else.
  • "This session" is not a concept. Recents were C's alone and go with it; nothing on the screen remembers the previous member.
